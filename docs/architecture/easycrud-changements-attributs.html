easy-crud — détail des changements

Comment on déclare une ressource admin via deux attributs — #[AsResource] (natif Sylius, sur le modèle) + #[AsAdmin] (easy-crud, sur la classe Admin) — sans rien casser de l'existant (YAML).

nouveau fichier ajouté modifié fichier existant renommé
L'idée en une phrase. Le modèle porte l'attribut natif Sylius 2 #[AsResource] (identité/alias de la ressource), et la classe Admin porte #[AsAdmin(resourceClass: …)] (la couche easy-crud). Ensemble ils remplacent les deux blocs YAML (config/routes.yaml + config/packages/sylius_resource.yaml). easy-crud régénère exactement la même configuration legacy (contrôleur SyliusCrudResourceController, grille, formulaires) qu'avant → zéro changement de comportement.
Évolution depuis la 1re version. L'attribut s'appelait #[AsEasyCrudAdmin] et construisait lui-même toute l'entrée de ressource. Après revue avec le lead, on s'appuie désormais sur le #[AsResource] natif pour l'identité de la ressource ; l'attribut easy-crud est renommé #[AsAdmin] (et entity: devient resourceClass:). Point clé technique : l'enrichissement ne peut PAS se faire dans un compiler pass — il doit rester en prepend() (voir §2bis).

1. Le résultat pour le développeur

Une ressource easy-crud passait de deux blocs YAML (souvent 30+ lignes) à une annotation sur l'Admin. Les méthodes statiques de boilerplate disparaissent.

Avant

# config/routes.yaml
admin_app_entity_post:
  resource: |
    alias: app.post
    section: admin
    templates: "@SyliusEasyCrudPlugin\crud"
    redirect: update
    grid: admin_post
    form: { type: App\Admin\PostAdmin, options: { context: $context } }
    vars: { all: {...}, index: {...}, update: {...} }
  type: sylius.resource
  prefix: admin
# + un bloc sylius_resource.yaml (classes...)

// App\Admin\PostAdmin.php
class PostAdmin extends AbstractAdmin
  implements ServiceSubscriberInterface, AdminInterface {
  public static function getSubscribedServices(): array { return []; }
  public static function getName(): string { return 'admin_post'; }
  public static function getEntityFqcn(): string { return Post::class; }
  public static function getDefaultSortColumn(): string { return ''; }
  public function configureFields(...) {...}
}

Après

# config — deux listes de chemins
sylius_easy_crud:
  attributes: { enabled: true, paths: ['%kernel.project_dir%/src/Admin'] }
sylius_resource:
  mapping: { paths: ['%kernel.project_dir%/src/Entity'] }

// App\Entity\Post.php
#[AsResource(alias: 'app.post')]
class Post implements ResourceInterface {...}

// App\Admin\PostAdmin.php — c'est tout
#[AsAdmin(resourceClass: Post::class, icon: 'newspaper', except: ['show'])]
final class PostAdmin extends AbstractAdmin
{
    public function configureFields(...) {...}
}

Plus de blocs YAML, plus de ServiceSubscriberInterface, plus de getName()/getEntityFqcn().

2. Le principe (tout se passe au build du conteneur)

Modèle + Admin annotés#[AsResource] + #[AsAdmin]
→
prepend() + Factoryscan des Admin, lecture de l'alias #[AsResource]
→
config legacy régénéréeressource sylius_resource + config de routage
→
routes sylius.resourceidentiques à l'ancien YAML

easy-crud scanne les Admin #[AsAdmin], lit l'alias de la ressource depuis le #[AsResource] du modèle (par réflexion), et alimente la config sylius_resource en prepend(). Sylius la transforme ensuite en paramètre sylius.resources puis en services via sa machinerie habituelle. Aucune décoration de service : on réutilise Sylius tel quel.

2bis. ⚠ Pourquoi prepend() et pas un compiler pass

C'est le point qui a dicté toute l'architecture. La tentation naturelle (et l'idée initiale) était : laisser #[AsResource] enregistrer la ressource nativement, puis l'enrichir après coup dans un compiler pass (réécrire controller/form/repository dans le paramètre sylius.resources). Ça ne marche pas, et on l'a vérifié dans le conteneur.

Ce que fait #[AsResource] nativement

Pendant le load() du resource-bundle, autoRegisterResources() scanne sylius_resource.mapping.paths et, pour chaque #[AsResource], écrit une entrée avec les défauts : controller = ResourceController, form = DefaultResourceType. Puis — toujours dans le load() — le driver de ressource matérialise les services par-ressource (le service contrôleur avec sa classe, le repository, et la sous-ressource de traduction).

La fenêtre de temps

prepend()tous les bundles
✅ seul endroit où l'on peut injecter dans la config sylius_resource
→
load() du resource-bundleautoRegister + le driver crée les services (contrôleur, repo, traduction) à partir de la config figée ici
→
compiler passes❌ trop tard : les services existent déjà
Résultat empirique d'un override en compiler pass (testé puis abandonné — la classe RegisterEasyCrudAdminsPass a été créée puis supprimée) :
  • le service contrôleur reste de classe Sylius\…\ResourceController → toute la logique easy-crud est court-circuitée (le $context, les actions ca:, la construction du form en showAction, l'autocomplete) ;
  • le repository reste le générique (pas le PostRepository du projet) ;
  • la sous-ressource de traduction n'est jamais créée (les modèles traduisibles cassent).
Modifier le paramètre sylius.resources dans un pass corrige bien le registre et le routage, mais pas les services déjà matérialisés par le driver.

La solution : prepend() + alias déjà déclaré

Le seul hook qui influence la config au moment du load() est le prepend() des extensions (il tourne avant tous les load()). easy-crud y déclare l'entrée complète (contrôleur SyliusCrudResourceController, form = l'Admin, repository, traduction) via prependExtensionConfig('sylius_resource', …), sous l'alias lu sur #[AsResource]. Et — détail décisif — autoRegisterResources() ignore tout alias déjà présent dans la config. Donc easy-crud « gagne » proprement : c'est lui qui possède l'entrée, et le driver matérialise les bons services dès le load().

Le rôle réel de #[AsResource] ici. Il fournit l'identité déclarative (l'alias) qu'easy-crud lit par réflexion. Son auto-enregistrement natif est court-circuité par notre prepend pour ces ressources précises — mais le modèle reste une ressource Sylius standard, déclarée avec l'attribut standard. C'est ce qui justifie les deux listes de chemins (attributes.paths pour les Admin, sylius_resource.mapping.paths pour les modèles).

3. L'API : les attributs + la configuration

#[\Sylius\Resource\Metadata\AsResource] sur le modèle natif Sylius

L'attribut Sylius 2 standard. On l'utilise pour déclarer l'identité de la ressource — principalement son alias (à conserver à l'identique lors d'une migration pour garder les noms de routes/URLs). Aucune operations: n'est nécessaire (easy-crud fournit son propre routage).

src/Metadata/AsAdmin.php renommé (ex-AsEasyCrudAdmin)

Attribut de classe (#[\Attribute(TARGET_CLASS)]) posé sur l'Admin. Il pointe sur le modèle via resourceClass (la classe porteuse de #[AsResource], plus forcément une entité) et porte la donnée admin :

resourceClass, alias (optionnel — défaut : l'alias du #[AsResource]), section, prefix, templates, controller, grid, defaultSort, defaultSortOrder, limits, repositoryMethod, repositoryArguments, permission, except, only, redirect, icon, header, subheader, breadcrumb, vars (passthrough libre), path. Tout est optionnel et retombe sur les défauts easy-crud.

src/DependencyInjection/Configuration.php modifié

  • Correction d'un bug latent : la racine était adeliom_sylius_easy_crud (incohérente avec l'alias d'extension) → sylius_easy_crud.
  • Ajout de l'arbre attributes: { enabled: false, paths: [] }. enabled est l'unique interrupteur (scan runtime et sortie du maker).
  • Côté projet, en plus : sylius_resource.mapping.paths (chemin des modèles #[AsResource], config native Sylius — vide par défaut).

4. Le moteur de traduction

src/Metadata/EasyCrudResourceFactory.php modifié

Helper pur (sans DI). build(array $paths) scanne les classes des dossiers d'Admin, garde celles qui sont des AdminInterface portant #[AsAdmin], et produit pour chacune :

$alias => [
  'registry' => [ // = bloc sylius_resource.resources.<alias>
     'driver' => 'doctrine/orm',
     'classes' => [ model, controller, form (= l'Admin), repository?, translation? ],
  ],
  'routing'  => [ 'prefix' => ..., 'config' => [ // = bloc resource: de routes.yaml
     alias, section, templates, redirect, permission, grid, form{type,options.context}, vars, except/only, path?
  ]],
]

Le modèle vient de #[AsAdmin]->resourceClass, la grille de Admin::getName(), le form = la classe Admin. Le repository est lu sur le modèle (#[ORM\Entity(repositoryClass:)]), la traduction si le modèle est TranslatableInterface. L'alias est lu sur le #[AsResource] du modèle (AsResource::toMetadata()->getAlias(), sinon dérivé <app>.<snake(short - "Resource")>, comme Sylius). #[AsResource] est requis (exception claire sinon, sauf alias explicite sur #[AsAdmin]).

src/DependencyInjection/SyliusEasyCrudExtension.php modifié

  • load() : traite la config, expose les paramètres sylius_easy_crud.attributes.enabled|paths.
  • prepend() : si activé, appelle la Factory puis prependExtensionConfig('sylius_resource', ['resources' => ...]) (cf. §2bis — c'est ce qui fait gagner easy-crud sur l'auto-enregistrement natif) et stocke deux paramètres : ...attributes.routing (pour le loader) et ...attributes.declared_aliases (pour exclure ces alias de la dépréciation). Résout %kernel.project_dir% et ignore les dossiers inexistants.

src/Routing/EasyCrudAttributesRoutesLoader.php nouveau + config/routes.yaml / config/services.yaml modifiés

Loader (calqué sur le CrudRoutesAttributesLoader de Sylius) qui rejoue chaque config de routage via le loader sylius.routing.loader.resource et applique le préfixe /admin. Les routes générées sont donc identiques à celles de l'ancien YAML.

Piège important. Un service taggé routing.route_loader n'est pas invoqué automatiquement — il faut l'importer explicitement. D'où l'ajout dans le config/routes.yaml du plugin : 
sylius_easy_crud_attributes:
    resource: 'Adeliom\SyliusEasyCrudPlugin\Routing\EasyCrudAttributesRoutesLoader'
    type: service
(Le projet importe déjà ce routes.yaml → rien à faire côté projet. Si enabled: false, le paramètre routing vaut [] → collection vide.)

5. AbstractAdmin / AbstractFormType

src/Admin/AbstractAdmin.php modifié

Les méthodes statiques deviennent concrètes et lisent l'attribut par défaut (le pattern « défaut = attribut, surcharge = méthode ») :

public static function getEntityFqcn(): string   // = attribut->resourceClass (sinon exception claire)
public static function getName(): string          // = attribut->grid ?? "admin_<snake(NomSansAdmin)>"
public static function getDefaultSortColumn()      // = attribut->defaultSort ?? ''
public static function getDefaultSortOrder()        // = attribut->defaultSortOrder ?? 'asc'
public static function getLimits()                  // = attribut->limits ?? [10,25,50]

L'attribut est lu via réflexion (mis en cache) sur static::class. Compatibilité : un Admin qui définit encore ces méthodes (tous les admins existants) les surcharge → comportement inchangé.

src/Admin/AbstractFormType.php modifié

Implémente désormais ServiceSubscriberInterface avec un getSubscribedServices(): [] par défaut. C'est la classe dont le constructeur réclame le $locator → c'est l'endroit logique. Les admins n'ont plus à le redéclarer (ils peuvent surcharger pour des services spécifiques).

Pourquoi on garde AdminInterface. C'est le marqueur d'autoconfiguration (tag sylius_easy_crud_admin) + le contrat, nécessaire à tout Admin (YAML ou attribut). L'attribut est un marqueur différent (« déclare la ressource ici »). On a seulement retiré le implements AdminInterface redondant des classes générées, car AbstractAdmin le porte déjà.

6. Le maker

src/Maker/CreateEasyCrud.php + src/Services/CrudMakerService.php + src/Resources/skeleton/Admin.tpl.php modifiés

make:easy-crud:create-crud se branche sur attributes.enabled :

  • activé → ajoute #[AsResource] sur l'entité (addAsResourceAttributeToEntity()) et #[AsAdmin] sur l'Admin généré (addEasyCrudAttributeToClass()), et n'écrit aucun bloc YAML.
  • désactivé → comportement historique (génère les YAML) + une dépréciation (cf. section suivante).

Le skeleton ne génère plus ServiceSubscriberInterface ni implements AdminInterface (portés par le parent).

7. Coexistence & dépréciation

Coexistence totale. Le système YAML est du Sylius pur, intact. La Factory ne tourne qu'en mode attribut et ne traite que les Admin annotés. On peut donc migrer une ressource à la fois, les deux styles cohabitent.

src/CompilerPass/DeprecateLegacyResourcesPass.php nouveau + src/SyliusEasyCrudPlugin.php modifié

Au build du conteneur, ce pass déclenche une trigger_deprecation pour chaque ressource easy-crud encore déclarée en YAML (détectée par : controller = SyliusCrudResourceController ou form = AdminInterface). Il exclut les ressources déclarées par attribut et les sous-ressources de traduction. Ainsi, un lead/dev qui met à jour le plugin voit ses dépréciations via bin/console debug:container --deprecations, même sans lancer le maker.

Deux canaux complémentaires de dépréciation : le maker (au moment de générer du YAML) et ce compiler pass (au build, couvre le YAML écrit à la main). Version placeholder : déprécié en 2.1, retrait en 3.0.

UPGRADE.md nouveau + skill nouveau

  • UPGRADE.md : guide de migration (tableau de correspondance YAML → argument d'attribut, étapes, vérif).
  • .claude/skills/easy-crud-migrate-to-attributes/SKILL.md : un skill Claude Code qui automatise la migration (trouve les Admin, transforme la config, nettoie le boilerplate, supprime les blocs YAML, vérifie). .gitignore ajusté (!.claude/skills/) pour livrer le skill avec le package.

9. Vérification effectuée

Via Docker (docker compose run --rm -e APP_ENV=dev php vendor/bin/console …), dans la test-application du plugin (Sylius 2.2.3).

  • PHPStan (niveau max) et ECS : verts sur tout le code ajouté/modifié.
  • End-to-end : un Admin (extends AbstractAdmin + #[AsAdmin(resourceClass: …)]) avec #[AsResource] sur l'entité génère 6 routes byte-identiques à l'ancien YAML (noms/paths/méthodes), avec :
    • service contrôleur = Adeliom\…\SyliusCrudResourceController (✅ pas le ResourceController natif) ;
    • repository = le vrai PostRepository du projet ;
    • sous-ressource de traduction présente ;
    • _sylius (grid/section/template easy-crud/vars) identique au YAML ;
    • HTTP 302 (redirection firewall, pas 404).
  • Coexistence : les ressources YAML existantes conservent leurs routes ; la dépréciation remonte pour le YAML legacy (attributs exclus, traductions exclues) via debug:container --deprecations.
